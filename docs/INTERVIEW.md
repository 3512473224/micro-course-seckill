# 面试手册：校园抢课系统（微服务高并发版）

## 一、简历描述（可直接抄）

> **校园抢课系统（微服务高并发版）**｜Spring Cloud Alibaba + Vue3｜个人项目
> - 微服务拆分：Gateway 网关 + user / course / enroll / seat 4 个业务服务，Nacos 做注册中心与配置中心，OpenFeign 服务间调用
> - 高并发抢课：Redis 预扣名额 + Lua 脚本原子扣减防超卖，SETNX 实现每人限抢 1 个名额；Sentinel 热点限流 + 熔断降级保护下游
> - 分布式事务：普通选课链路用 Seata AT 模式（@GlobalTransactional），建单 + 远程扣名额要么都成功要么都回滚，并提供无事务对比接口
> - 网关统一鉴权：GlobalFilter 校验 Token，白名单放行登录，下游服务经 X-User-Id 透传免重复鉴权
> - 课程列表 Redis 缓存（Cache-Aside）；MySQL 一库多表演示，注释标注生产分库方案；Docker Compose 一键编排 10 个容器

## 二、深挖 Q&A（面试官最爱问的 8 个）

### Q1：Nacos 用的是 AP 还是 CP？和 CAP 怎么对应？
A：Nacos 的服务发现默认是 **AP 模式**（牺牲强一致，保证可用性——注册中心挂了 half 都不能影响服务调用）。
它也支持 CP（基于 Raft，用于配置中心场景的强一致需求）。我们的用法：服务发现走默认 AP，
配置中心（mall-common.yaml）的场景对一致性要求不高，AP 够用。对比：Eureka 也是 AP，
Zookeeper 是 CP（选主期间不可写）。选型理由：注册中心的本质是"尽量可用"，宁可读到稍旧的
实例列表，也不能因为少数节点故障导致整个服务发现不可用。

### Q2：Feign 的超时和重试是怎么配的？默认行为有什么坑？
A：Feign 默认 connectTimeout=10s、readTimeout=60s（生产必须调小，否则下游慢会把上游线程池拖满）。
重试默认是关闭的（Feign 默认 Retryer.NEVER_RETRY），但如果引入了 Spring Retry 会变成
"默认重试 1 次"。坑：**非幂等接口（建单、扣名额）绝不能盲目重试**，否则一次用户点击变两次扣减。
我们的做法：抢课链路靠"限购 SETNX + Lua 原子"保证幂等；普通选课接口重试需调用方保证幂等
（本演示未开 Feign 重试，注释里有说明）。

### Q3：Sentinel 的限流算法有哪些？你用的 QPS 直接拒绝是什么？
A：Sentinel 限流分两大维度：
1. **按 QPS**（令牌桶思想的变体：统计窗口内计数，超了就拒绝/排队）和**按并发线程数**
   （信号量，适合 RT 很长的慢调用，防止线程堆积）。
2. 流控效果：**直接拒绝**（快速失败，适合秒杀）、**WarmUp**（冷启动预热，按斜率放行，
   防缓存没建好时被打爆）、**匀速排队**（Throttling，让请求匀速通过，削峰填谷）。
我们给 `seckill` 资源配的是 QPS=200 直接拒绝——抢课请求处理极快（纯 Redis 操作），
直接拒绝是最合适的；被拒绝的走 blockHandler 返回"活动火爆请稍后再试"，而不是堆积。

### Q4：Seata AT 的二阶段原理？和 XA 有什么区别？脏写怎么防？
A：AT 是一阶段做"业务 SQL + 写 undo_log（前后镜像）"然后**各自提交本地事务**，
二阶段根据全局事务成败做"删 undo_log（提交）/ 反向补偿（回滚）"。和 XA 的区别：
XA 是强一致的两阶段提交，一阶段就锁住资源不释放，并发低；AT 一阶段本地事务直接提交、
只用**全局锁**防脏写，并发高得多，但理论上有极短的数据不一致窗口（最终一致）。
脏写防护：分支事务提交前会尝试持有记录的全局锁，持有失败就回滚重试；但注意**全局锁
只对 Seata 分支事务有效**，如果有人绕开 Seata 直接写 DB，AT 防不住——所以要求
所有写都走分支事务。

### Q5：为什么 Lua 脚本能防超卖？和分布式锁比好在哪？
A：Redis 是**单线程执行命令**的，一个 Lua 脚本从开始到结束不会被其他客户端打断。
"查名额→判断→扣减"三步如果拆成三条命令，高并发下两个请求可能同时读到 stock=1
然后都扣减成功→超卖；Lua 把三步打包成原子操作，第二个脚本看到的是扣减后的值。
对比分布式锁（Redisson）：锁方案要多两次网络往返（加锁/解锁），且锁粒度不好控制时
吞吐上不去；Lua 是单机内存操作，轻松 10w+ QPS。注意 Lua 里**不要写耗时逻辑**，
会阻塞整个 Redis。

### Q6：为什么鉴权放网关，而不是每个服务自己验 Token？
A：三点：①收口——鉴权逻辑只写一处，不会出现"某个服务漏验"的安全事故；②下游专注业务，
网关验签后把 userId 写入 X-User-Id 透传；③非法请求在入口就被 401 挡掉，保护业务服务。
代价是网关变单点——生产部署多实例 + 前面挂 LB/SLB 解决。另外注意：服务不能被外网直调
（安全组/内网隔离），否则攻击者可伪造 X-User-Id 绕过鉴权，生产可加内部签名或 mTLS。

### Q7：分布式事务除了 Seata AT，还知道哪些方案？怎么选？
A：① **TCC**（Try-Confirm-Cancel）：业务侵入大，要手写三段逻辑，但无锁、性能好，
适合对一致性要求极高且能接受开发成本的核心链路；② **Saga**：长事务拆成多本地事务，
失败时反向补偿，适合流程长、参与方多的场景（如订单→支付→物流），但要处理"空补偿/
悬挂"问题；③ **MQ 最终一致性**（本地消息表/RocketMQ 事务消息）：高并发首选，
秒杀/抢课这种场景就该用它而不是 Seata；④ XA：强一致但并发差，基本淘汰。
选型口诀：**高并发用 MQ，低并发强一致用 Seata AT，复杂长流程用 Saga/TCC**。
我们的项目正好演示了这种分层：抢课走 Redis+补偿（类 MQ 思想），普通选课走 Seata AT。

### Q8：一个请求从浏览器到抢课成功，完整链路走一遍？
A：浏览器 → nginx（前端容器 :80）→ 网关 :8080（GlobalAuthFilter 验 Token→写 X-User-Id→
按 /api/seckill/** 路由到 course-service）→ SeckillService：查活动时间→SETNX 限购→
Lua 原子扣 Redis 名额→Feign 调 enroll-service 建选课单（本地 insert）→enroll 再 Feign
调 seat-service 扣 DB 名额→逐层返回 Result。任一步失败都转成中文错误信息抛给前端。
（普通选课链路多一步：enroll-service 方法上有 @GlobalTransactional，Seata TC 协调
enroll/seat 两个分支，要么都提交要么都回滚。）

## 三、现场演示话术（2 分钟讲清亮点）

**演示 1：秒杀防超卖（1 分钟）**
1. 先预热名额：`POST /api/seckill/init/1001`（把 DB 的 100 个名额加载到 Redis）
2. 跑压测脚本（README 里有）：120 个并发抢 → 只有 1 个成功（每人限购 1）
3. 查剩余：`GET /api/seckill/stock/1001` → 99，查 enroll_order 表 → 只有 1 条
4. 话术："120 并发下无超卖、无重复抢课，靠的是 Lua 原子扣减 + SETNX 限购"

**演示 2：Sentinel 熔断降级（30 秒）**
1. 正常调一次普通选课，成功
2. `docker stop course-seat`（停掉名额服务）
3. 再调选课 → 快速返回"名额服务繁忙（已触发熔断降级），请稍后重试"，而不是卡 60 秒超时
4. 话术："Feign+Sentinel 的 fallback 让故障快速失败，保护上游线程池不被拖死"
5. `docker start course-seat` 恢复

**演示 3：Seata 分布式事务回滚（30 秒）**
1. 调 `/api/enroll/create` 传一个**名额不足**的 courseId → 返回"课程名额不足"
2. 查 enroll_order 表 → **没有**残留选课单（被 Seata 回滚了）
3. 再调 `/api/enroll/create-no-seata` 同样参数 → 同样报错，但表里**多了一条脏数据**
4. 话术："同一个失败场景，有 Seata 的数据干净，没有的留下脏单——这就是分布式事务的价值"
